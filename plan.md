## VM Cloud storage and Minecraft connection details
Cloud files are stored persistently on the configured host path (default `~/.local/share/tmpserver/cloud`) and exposed through owner-authenticated list, streamed upload, download, and delete endpoints. Cloud file uploads have no fixed per-file application cap; actual capacity is limited by available host storage and the network path. The Minecraft connection panel displays the host agent's `PUBLIC_HOSTNAME`; set it to the direct IP `86.129.220.212` (the latest Geyser STUN mapping provided on October 25, 2026) to show that IP, with Java port `25565` and Bedrock port `19132`. If the ISP address changes, update this setting and restart the agent. The previous 10-player cap was removed; the server now accepts up to 1000 configured players, which is the practical limit for this VM rather than an unsafe claim of infinite capacity.

## Stable host-agent integration
The GitHub Pages frontend is a static client that talks directly to the owner's stable host-agent URL. The Actions workflow reads `VITE_HOST_API_URL` from a repository variable, falling back only to the owner's stable `https://agent.tmpserver.com`; it must never embed an ephemeral Quick Tunnel hostname. Rebuilding Pages is required after changing this value. The agent keeps its owner-only Supabase validation and chunked, bounded-request Cloud protocol, including compatibility with Python runtimes where the deprecated `cgi` module is absent.

## Website directory, deletion, and hosted routing
Link-only entries accept absolute HTTP/HTTPS URLs, remain separate from server services, and delete only their registry records. Hosted sites continue to use Caddy; active-site deletion removes the generated route before removing files, while route failures preserve the entry/files and return an actionable error. A root-owned, narrowly scoped Caddy sync helper validates only generated static-site routes and is callable through one exact sudoers rule; it cannot accept arbitrary Caddy directives. Active static content is made readable but not writable by Caddy, symlinks are rejected, and the sibling Cloud backup directory stays private. Inactive hosted deletions do not need a Caddy reload.

## Rolling Minecraft backup
The host creates `minecraft-latest.tar.gz` in its configured Cloud storage path atomically after pausing automatic world saves and flushing Paper with `save-all flush`. A persistent systemd timer runs this backup daily at 09:00 UTC and catches up after host downtime; the same installed executable powers asynchronous manual backups and controlled lifecycle/settings operations. Backups have a generous six-hour runtime guard plus a five-minute TERM-cleanup grace, not a per-file size cap; a failed/interrupted backup leaves the previous archive intact. The game stays online during a manual snapshot, and the script attempts to restore Paper saving on cancellation/failure. Settings are validated before host mutation; the owner can configure view distance (2–32), simulation distance (2–32), maximum players (1–1000), and whitelist enforcement. Settings changes back up before stopping/restarting Paper, then wait for RCON readiness, and report backup, apply, restart, and refresh failures truthfully.

## Owner-only Minecraft keep inventory and manual backups
The live Paper server includes `TMPKeepInventory`, a small event plugin keyed to the owner's Floodgate UUID so only `.BroodyFoil99867` keeps inventory, levels, and experience after death. Cloud and Settings backup actions start a background host job and poll status, so a large archive does not hold a Cloudflare HTTP request open. The UI refreshes the Cloud file list and backup metadata after successful completion.

## General website links and large VM storage uploads
The Websites panel keeps hosted static sites as a distinct type and adds link-only records for arbitrary absolute HTTP/HTTPS URLs. Link-only entries are stored in the existing website index, open as safe external links, and never create Caddy routes, hosting directories, or VM service telemetry. Existing records without a kind remain hosted sites. Each external link can also display a selectable Running, Updating, Down, Maintenance, or Unknown simulated state; the state is stored in browser local storage and is labeled as visual-only, not a live check or host operation.

Cloud files and hosted-site ZIPs remain owner-only and are uploaded in bounded 8 MiB chunks; neither has a fixed per-file application-size cap. Cloud files finalize atomically, and ZIP deployments validate archive paths before atomically replacing a site's public directory. The UI displays used and available host storage. Real host filesystem capacity, network availability, and any proxy/account transport limits still apply; ZIP archives also retain path and 10,000-entry safety checks.
